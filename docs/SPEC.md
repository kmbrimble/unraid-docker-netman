The host docker CLI can also be used from this container via `docker run --rm -v /usr/bin/docker:/usr/local/bin/docker:ro -v /var/run/docker.sock:/var/run/docker.sock alpine docker ...` (this container's own docker CLI is 20.10 and lacks the advanced `--network` syntax — never use it for network tests). `gh` is authenticated as `kmbrimble`.

## Purpose

Unraid's dockerMan lets a container have ONE network (Network Type + Fixed IP + MAC). This plugin lets each container have ADDITIONAL networks, each with optional fixed IP, alias, and (where possible) MAC, and makes them persist across reinstall / force update / "Previous Apps" — by writing them into the container's own template XML, which dockerMan already persists and re-applies. No runtime hook, no plugin database.

## Verified facts (do not re-derive; build on these)

1. `xmlToCommand()` in `/usr/local/emhttp/plugins/dynamix.docker.manager/include/Helpers.php` builds the command via `sprintf` in this order: `--name`, network, `--ip`, cpuset, pids, privileged, `-e` vars, tailscale stuff, `-l` labels, `-p`, `-v`, `--device`, **ExtraParams**, image, **PostArgs**. ExtraParams are AFTER the template's network flags; PostArgs are appended after the image, so `&& docker network connect ...` runs after `docker run -d` returns. Force update, reinstall, and the Update Container form all go through this function.
2. `hasNetworkParam($xml['ExtraParams'])` (regex `--net(work)?[= ]`) — if ExtraParams contain any `--network`/`--net`, dockerMan **omits its own `--net=`** entirely but STILL emits `--ip=<Fixed IP>` and (when no MAC) nothing else. So on the ExtraParams path the plugin must emit the primary network too, in SHORT form (`--network br0`) so the bare `--ip` binds to it. Emitting `--network name=br0,ip=…` while dockerMan also emits `--ip` fails: `conflicting options: cannot specify both --ip and per-network IPv4 address`.
3. When the template has a MAC set (MyMAC) and primary is not host/none, dockerMan itself emits `--network=name=<net>,ip=<ip>,mac-address=<mac>` (advanced syntax) — unless ExtraParams already has a `--network`, in which case it strips the MAC param and emits nothing for network. Handle this: on the ExtraParams path, if the template has MyMAC, emit `--network name=<primary>,mac-address=<mac>` (NOT ip=, since dockerMan still emits bare `--ip`). TEST THIS CASE on a scratch container before relying on it; if bare `--ip` + advanced-form primary conflicts, fall back to the PostArgs path for containers with MAC set.
4. Docker (CLI 29.5.2 host) refuses `--network bridge --network <user-defined>` at create: `cannot attach both user-defined and non-user-defined network-modes`. So containers whose primary is the default `bridge` (or host/none/container:) CANNOT use the ExtraParams path.
5. `docker network connect --ip X --alias Y <net> <container>` works after create, persists across stop/start and reboot (as long as the container isn't recreated), and name resolution works from peers on that network. `docker network connect` has NO mac-address option (verified `--help`): options are `--alias --driver-opt --gw-priority --ip --ip6 --link --link-local-ip`.
6. Advanced syntax `--network name=<net>,ip=<ip>,ip6=,alias=,mac-address=,link-local-ip=,driver-opt=,gw-priority=` works on this host for user-defined primaries (tested: `--net=br0 --ip=192.168.0.250 --network name=proxynet,ip=172.18.0.252` → both attached with correct IPs).
7. Page system: `AddContainer.page` / `UpdateContainer.page` have no `Menu=` so no plugin can add tabs to them and there is no hook in CreateDocker.php. BUT `DefaultPageLayout.php` evals every `Menu="Buttons"` page inside `<head>` on EVERY page load (see `/usr/local/emhttp/plugins/ipmi/IPMIButton.page` — it is a pure `<script>` injector with `Menu="Buttons:2"`, `Link="nav-user"`, `Markdown="false"`). This is the supported, non-patching injection vehicle. `.page` files must sit in the plugin's installed root (non-recursive glob).
8. dockerMan form field names (CreateDocker.php): `select[name=contNetwork]` (onchange `showSubnet(this.value)`), `input[name=contMyIP]`, `input[name=contMyMAC]`, `input[name=contExtraParams]`, `input[name=contPostArgs]`, `input[name=contName]`. Form rows are dl/dt/dd-style generated from markdown-ish `_(Label)_:` / `: <input>` blocks. Existing JS globals include `drivers` (network→driver map) and `showSubnet()`; the form is submitted via a `#dockerTemplate` form to the same page (POST with `contName`). Read CreateDocker.php lines ~800-860, ~1160-1200, ~1640-1760, ~1980-2020 to see exactly how the network rows, MAC handling and submit work before writing the injector.
9. User templates live at `/boot/config/plugins/dockerMan/templates-user/my-<Name>.xml` with `<Network>`, `<MyIP>`, `<MyMAC>`, `<ExtraParams>`, `<PostArgs>` elements (xml-encoded). Reading them: `xmlToVar()` in Helpers.php.
10. `/usr/local/emhttp` is restored from the OS image on every boot; plugin files installed via the .plg's txz are re-installed at boot by the plugin system, so no boot re-patching is needed for a non-patching plugin.

## Serialization design (the core)

A container's "additional networks" are stored ONLY in its template, inside a marker-delimited block so the plugin can find, parse, rewrite, and remove them without disturbing anything the user typed by hand:

- ExtraParams path (primary is user-defined: br0, br0.66, proxynet, claudenet, any custom bridge/ipvlan/macvlan): the block is
  `--network <primary> --network name=proxynet,ip=172.18.0.5,alias=foo --network name=other …`
  Wrap it so it's recognisable, e.g. leading token `--label multinet=1` is NOT acceptable as a marker because labels change container identity; instead use a pure-text marker that docker ignores? Docker CLI does not ignore unknown text, so the marker must be derived: the plugin recognises its own block as "the maximal run of `--network …` tokens in ExtraParams whose first element is `--network <primary>`" and additionally stores a `<!-- multinet -->`-style hint? The template XML is regenerated by dockerMan from POST fields so XML comments won't survive. DECISION: keep a small sidecar `/boot/config/plugins/unraid-multinet/state.json` keyed by container name holding the canonical desired list (net, ip, alias, mac) purely as a parse aid and for the overview page; the template ExtraParams/PostArgs remain the thing that actually takes effect. On read, parse the template first (truth), and use the sidecar only to disambiguate. If the template's ExtraParams contain a `--network` token the plugin did not write (not matching what state.json says it wrote), the UI must show it as "manually managed" and refuse to rewrite ExtraParams for that container, offering PostArgs instead.
- PostArgs path (primary is `bridge`, `host`, `none`, `container:*`, or any case where ExtraParams path is unusable): the block is
  `&& docker network connect --ip 172.18.0.5 --alias foo proxynet <ContainerName> && docker network connect … other <ContainerName>`
  appended to whatever PostArgs the user already has (if the user's PostArgs don't start with `;`/`&&`/`|`, prepend `&&`? — NO: dockerMan appends PostArgs verbatim after the image, so the user's existing PostArgs are the container's CMD args unless they start with `;`/`&&`. Handle: if existing PostArgs is non-empty and does not begin with `&&`/`;`/`|`, our block still goes AFTER it and starts with ` && ` — that is correct shell semantics: `docker run … image <userargs> && docker network connect …`.) Container name is the template's `<Name>`. MAC unsupported on this path; the UI must disable the MAC field when this path will be used and explain why.
- Choose the path automatically from the primary network; show which path is in effect in the UI. Both paths must round-trip: parse → edit → serialize → parse gives the same result.
- Never emit `--network bridge`. Never emit an advanced-form primary with `ip=` (see fact 2).
- IPs: validate against the target network's subnet(s) from `docker network inspect`; optionally warn if the IP is inside the network's `IPRange` (Docker's dynamic pool) or already in use by another container's endpoint.

## Deliverables

### A. Plugin files (`plugin/` in repo → installed to `/usr/local/emhttp/plugins/unraid-multinet/`)

1. `MultiNetInject.page` — `Menu="Buttons:5"`, `Link="nav-user"`, `Markdown="false"`. Pure `<script>` (and a small `<style>`), no visible button. Only acts when `location.pathname` matches `^/Docker/(AddContainer|UpdateContainer)`. Injects a section directly BELOW dockerMan's MAC row (find `input[name=contMyMAC]` and walk up to its row container; match dockerMan's dl/dt/dd or table markup exactly so it looks native — inspect the rendered DOM over SSH by fetching the page HTML if needed, or read how CreateDocker.php renders `_(Fixed IP address)_:` rows). Section = "Additional networks" with repeating rows: network `<select>` (populated via AJAX from the plugin endpoint, excluding host/none/bridge/container: and the currently selected primary), Fixed IP text, Alias text, MAC text (disabled on PostArgs path), remove button; "Add network" button; a read-only line showing the exact ExtraParams/PostArgs fragment that will be written and which path is in effect. Re-evaluate path whenever `contNetwork` changes. On page load, parse existing `contExtraParams`/`contPostArgs` values into rows and HIDE our block from the visible fields (show the user's own remaining params). On submit (hook the form's submit / the Apply button — find how dockerMan submits, it may call a JS function before `form.submit()`), re-compose the visible field values + our block into `contExtraParams`/`contPostArgs` before the POST proceeds. Must also work on the Update Container page for existing templates, and must not break the page when the plugin endpoint is unreachable (fail soft: section shows an error, form still submits untouched).
2. `MultiNet.page` — `Menu="Docker:3"`, `Title="Networks"`, `Tag="sitemap"` (or similar icon) — a tab on the Docker page. Two parts:
   - Networks table: name, driver, subnet/gateway/ip-range, containers attached (from `docker network inspect`), delete button (refuse if containers attached; never allow deleting bridge/host/none/br0*). "Create network" form: name, driver (bridge default; ipvlan/macvlan with parent select from host interfaces is a bonus), subnet, gateway, ip-range, internal flag. Uses `docker network create`.
   - Containers matrix: one row per dockerMan template (templates-user) showing primary network / IP / MAC (read-only, from template) and its additional networks (editable inline with the same row widget as the injector — share the JS), the path in effect, and LIVE state from `docker inspect` (which networks it is actually on right now). Per row: Save (rewrites the template XML's ExtraParams/PostArgs via the endpoint) and "Apply now" (runs `docker network connect/disconnect` with `--ip/--alias` to make live state match desired without recreating the container — this is the replacement for the user's current manual CLI step), plus a status chip: in-sync / drift / not running. A page-level "Apply all" button.
3. `include/api.php` — the JSON endpoint (POST only, CSRF: use Unraid's `$_POST['csrf_token']` check like other plugins — look at how secretsman's store_api.php does it). Actions: `networks` (list + inspect summary), `network_create`, `network_delete`, `containers` (templates + parsed desired + live), `get` (one container), `save` (container, rows) → rewrites template XML using the same parse/serialize library, `apply` (container) → reconcile live state, `preview` (rows + primary + name → fragment). Never shell-interpolate unescaped user input: `escapeshellarg` everything.
4. `include/multinet.php` — pure library: parse/serialize for both paths, path selection, XML read/write helpers (preserve everything else in the template byte-for-byte where possible — use SimpleXML like Helpers.php does, and write with the same `xml_encode` semantics; check what dockerMan does to `&&` in `<PostArgs>`), docker CLI wrappers. No side effects at include time. Unit-testable under PHP CLI.
5. `README.md` at plugin root (Installed Plugins page renders it), `LICENSE` (GPL-2.0 like Unraid plugins commonly use, or MIT — your call, say which).
